# JV-2080 Control (Max for Live)

A Max for Live MIDI effect that edits a Roland JV-2080 over SysEx from Ableton Live.
It is published on maxforlive.com (https://maxforlive.com/library/device/7406/jv-2080-control)
and has outside users. Goal: a reliable editor for the JV-2080, and also the JV-1080 and
XP-50/80. These share model ID `0x6A`.

## Layout

- `device/JV 2080 Control.amxd`: the main device, **unfrozen**. It is a binary header followed by patcher JSON.
- `device/JV_*.maxpat`: abstractions loaded as bpatchers: `JV_Wave`, `JV_Pitch`, `JV_Filter`, `JV_VCA`, `JV_LFO`, `JV_CTRL`, the patch-wide pages `JV_FX`, `JV_PATCH`, `JV_CTRLCOMMON`, and `JV_LIBRARY`, `JV_PERFORM` (one instance each).
  Each runs once per tone. The tone's address byte (`16/18/20/22` = `0x10/0x12/0x14/0x16`) comes in on inlet 2.
- `device/jv_sysex_queue.js`: a Max `js` object (ES5) in front of the main `midiout`. **All SysEx must go through it**: wire it to inlet 1, or use `s ---sysex` inside subpatchers. It sends one message every 10 ms and merges queued messages for the same address. Without it, the JV reports "MIDI buffer full".
- `device/jv2080_params.js`: the JV-2080 **parameter address map** (patch common + tone, manual pp.189–190): offset, range, nibble size, display rule (`add`/`mul`/`enum`/`char`/`note`) and the value lists. This is the single source of truth for addresses and ranges. Transcribed by hand; tests check that it covers every byte once.
- `device/jvparam.js`: **the only way the device sends a single parameter edit.** Each control feeds a `js jvparam.js a1 a2 a3 a4` box (inlet 0: value, or bang to resend for push; inlet 1: tone address byte). `a3 = -1` means the tone address arrives on inlet 1, and nothing is sent until it does. A 5th argument `2` sends the value as two nibbles (wave number). It is **self-contained, no `include()`**. Freezing embeds included files once per *instance*, and with ~80 senders that made the frozen device 9.5 MB; the test enforces this. Don't add `sxformat` senders. Use `jvparam` with the parameter's address.
- `device/jvbank.js`: the program block's bank select. The stored `Bank` parameter is a hidden 23-entry `live.menu` (USER, PR-A…PR-E, CARD, XP-A1…XP-H2; MSB/LSB per manual p.184). The visible `BankDisplay` is a Hidden-parameter `live.menu` rebuilt from the Setup board slots (`r ---boards`). It sends CC0/CC32 on channel 1 through its own `midiout`, then bangs the program number (`pgmout`). `ctlin 0` / `ctlin 32` let it follow the JV's bank silently (`set`).
- `device/jvreceive.js`: **read-back** (#6). It taps `midiin`, sends the 5 RQ1s for the temporary patch on `get`, decodes the DT1 replies and writes each value to its control through `jv2080_bindings.js` (`patcher.getnamed(path).subpatcher().getnamed(varname)`). Controls are set *with* output, so stored values stay consistent, while the queue is muted (`mute 1/0`) so nothing goes back to the JV. It sends the patch name to the name field (`fromjv …`, outlet 2) after a read or a name edit on the JV. The name field is the embedded bpatcher `NameBlock` (textedit `PatchName` + `jvname.js` + 12 stored-only `Patch Name n` numboxes): typed characters go straight to their `jvparam` senders, and the name has **no binding on purpose**, so Send and the on-load push never overwrite the JV's patch name. **Send** (and the on-load push: the hidden push button `obj-20` → `send`) is the reverse: `send` reads every bound control (`getvalueof`), converts it to raw bytes with the bindings, and writes one DT1 per run of consecutive addresses (about 11 messages, 60 ms apart; `tests/jvreceive.test.js` checks Get → Send reproduces the dump). Parameters without a binding are not sent, so **every new control needs a binding** or Send skips it. It's triggered by the **Get** button and, if enabled on the Setup page, 300 ms after a program change (`r ---bangpgm`). Program changes during the first 1.5 s after load are ignored (`gate 1 0` opened by `live.thisdevice` → `delay 1500`): at load the saved set wins, so the restored program change must not trigger a read before the on-load push at 1 s.
- `device/jvsysex.js`: pure ES5 library (Max `include()` or Node `require`) for building DT1/RQ1 (7-bit addressing, checksums), parsing replies into named parameters (`parse` → `decode`), display values, and converting between control values and raw values for a binding (`fromControl`/`toControl`, wave group menu helpers).
- `device/jv2080_bindings.js`: **generated** by `tools/bindings.py`. For every control in the patches it records which parameter it sends, the bpatcher path (`Pitch_{n}`, `TVF_{n}`, `WG_{n}`, `VCA_{n}`, `ToneMix`), the control's varname and the math between control and raw value. Regenerate after patch edits; `--check` fails if it's stale. The tracer also flags controls whose range exceeds the JV's.
- `device/jvwavenames.js` + `device/jv2080_names.js`: wave names under each Wave dial (#30). Each `JV_Wave` sends `wave <tone address> <group 0-20> <number>` (`pak` → `s ---wavename`), and **one** `jvwavenames.js` in the main patch looks up the name and sets the section's `WaveName` comment. One instance so freezing embeds the names only once. `jv2080_names.js` is **generated** by `tools/import_wave_names.py` from Roland's board documents (copyright Roland). The committed file is the maintainer's import of boards 01–11 (his decision). Regenerate it with the script. **Never write wave or patch names into the repo by hand.**
- `device/jv_wavegroup.js`: builds each tone's short Wave group menu from the expansion board setup.
- `diagnostics/JV SysEx Monitor.amxd`: a standalone diagnostic device that receives SysEx (sysexin + midiin) and sends RQ1 test requests. It proved that Live 12 delivers SysEx to Max for Live, and that one track can send and receive (#6).
- `tests/fixtures/`: real JV dumps for parser tests.
- `tests/`: Node tests that mock the Max `js` globals. Run them with `node tests/<file>.test.js`.
- `tools/maxjson.py`: loads and saves patchers in Max's exact formatting, so a file that is loaded and saved unchanged stays byte-identical. Use it for structural edits rather than splicing text.
- `tools/validate.py`: checks that patch lines point at existing boxes and valid inlets/outlets, and that parameter long names are unique. Run it after every patch edit. When adding boxes, derive new ids from the patcher's current maximum; never hard-code them.
- `tools/check.sh`: runs every offline check (validate, bindings `--check`, all Node tests). CI runs it on every PR (`.github/workflows/check.yml`).
- `tools/amxd.py`: `unfreeze` splits a frozen device into source files. `textconv` prints the JSON for git diffs.
- `docs/JV-2080_OM.pdf`: Roland owner's manual. It is gitignored; download it from
  https://static.roland.com/assets/media/pdf/JV-2080_OM.pdf. It is a scan with no text layer, so read the pages as images.
  MIDI Implementation starts on p.184, the parameter address map is on pp.188–194, and the checksum example is on p.193.
- `dist/`: frozen release builds. These are gitignored and get attached to GitHub Releases.

## Editing patches

- Target: **Live 12 + Max 9** or newer. The device is saved with Max 9.1, in the 4-space JSON layout, and `tools/maxjson.py` keeps that layout. JavaScript may use the `v8` object (modern JS). The existing `js` object (`jv_sysex_queue.js`) keeps working.

- Patchers are JSON, so edits can be made directly. Keep the `"id"` values unique within a patcher, and make every
  `lines` entry refer to existing ids and valid inlet/outlet indexes.
- After any edit, check that the file still parses as JSON. For the `.amxd`, the JSON starts after the `ptch` chunk header.
  If the payload length changes, update the 4-byte little-endian length that follows `ptch`.
- Drawing order: in a patcher's `boxes` list, **earlier boxes are drawn on top**. The section panels are ordinary boxes, not background ones, so a new UI box appended at the end ends up hidden behind the panel. Insert new visible boxes at the front of `boxes`.
- Left column layout, top to bottom: the Patch / Perform switch (`ModeSwitch`), the program block on a dark background panel (`ProgramPanel`, `background 1`, same grey as the section panels) with (bank menu + program number, `PatchName`, **Send** / **Get** square `live.text` buttons (`rounded 0`) in button mode → `route bang` / `sel 1`; Send bangs the hidden push button `obj-20`, which is also the on-load push target), then the tone switches/levels (`ToneMix`, no label; hidden in Perform mode), then the Effects On/Off buttons (no label).
- The **FX** page (`JV_FX.maxpat`, button `FXButton`) is patch-level: FX on hides everything, switches LFO and Setup off and shows `FX`; any tab change, LFO or Setup switches it off (`set 0`). Its senders use fixed addresses: `js jvparam.js 3 0 0 <off>` for patch common, `3 0 <tone byte> <off>` for the per-tone outputs (reverb send at tone offset 0x80 is `<tone byte + 1> 0`). `bindings.py` traces them as block `common` (tones `[]`) or the tone. `jv2080_efx.js` is the EFX table: labels and value kinds per type in the **manual's order** (pp.168–172), which is *not* the order the JV sends them in. The wire order and ranges were measured on a JV-2080 (`docs/efx_survey.json`); `tools/efx_survey.py` writes them into the generated `MEASURED` block. The JV sends EFX values as an index into the parameter's value list (Low Gain +15 dB = 30); some slots are unused (e.g. chorus types skip the flanger's feedback slot). Kinds with uneven, undocumented steps (rate, pre delay, delay times) show raw until measured (#51). `jvfx.js` (include) labels the 12 EFX dials per type (`_parameter_shortname`, `active`), converts dial 0–127 ↔ raw (the dial's full travel covers the range), writes the value text under each dial (`EFXValue<n>`) and feeds the senders; Get uses the binding op `["efx", slot]` with the EFX Type menu's value. It also names the type for `jsui jvfxroute.js`, the routing graphic (display only, fed by `prepend tone n …`, `efx …`, `chorus …`, `reverb …`; the Effects On/Off toggles send `efx|chorus|reverb on 0/1` via `s ---fxsw`, and a switched-off unit is drawn dashed). `jvreceive.js` follows the JV's EFX/CHORUS/REVERB buttons (System Common `08–0A`) onto the Effects On/Off toggles (bpatcher varname `EffectsSwitch`).
- The **Patch** page (`JV_PATCH.maxpat`, varname `PatchPage`, button `PatchButton`). Button column: Tone tabs and LFO (per tone) at the top; FX, Patch and Setup (patch-wide) at the bottom works like FX (patch-level; FX and Patch switch each other off). Fixed-address senders like FX (patch tempo uses the nibble form `… 0 44 2`; `bindings.py` traces JV_FX and JV_PATCH alike). `jsui jvstruct.js <pair>` draws the Structure Type diagram (copied from the JV-2080's Struct page; R+ = an R block the JV draws filled (Types 6–10); Types 8 and 10 also route Tone 2 past R) and greys the Booster menu outside Types 3/4 (`active`); `jsui jvzones.js` draws the tones' key/velocity zones and is draggable: it outputs `<varname> <value>` (`route T1KeyLo …` → the zone control, which sends as usual). Key ranges are enum `live.numbox`es with JV note names (0 = C-1, 60 = C4; Live's own MIDI display would show C3).
- The **Ctrl** page (`CtrlButton`, below LFO) is per tone like LFO: it adds 8 to the tab index (`sel 0 … 11`) and shows `CTRL_n` (`JV_CTRL.maxpat`: controller matrix tone `0x15–0x2C`, control switches `0x10–0x14`) together with `CtrlCommon` (`JV_CTRLCOMMON.maxpat`, one instance: patch control sources 2/3, hold/peak, EFX control, patch common `0x1D–0x20`, `0x3A–0x3F`). LFO and Ctrl switch each other off; wherever LFO is switched off (Setup, FX, Patch) Ctrl goes off too. With it, every patch parameter except the name has a binding.
- The **Library** page (`JV_LIBRARY.maxpat`, varname `LibraryPage`, button `LibraryButton`, patch-level like FX/Patch) runs `jvlibrary.js`: backup of the whole user memory with one RQ1 per block (system + scale tunes, 32 performances × 17, 2 rhythm sets × 65, 128 patches × 5 = 1332 blocks, pp.188–191), restore of `.syx` files (only DT1s for `00 00 …`, `10 …`, `11 …` with a valid checksum; an automatic backup next to the file first; confirmation via the `RestoreNow` button, greyed out until asked), and recording of a bulk dump started on the JV. It gets `midiin` bytes, sends through the queue, and tells `jvreceive.js` `busy 1/0` so Get and Send wait. File names are passed as one symbol (no spaces in default names). Favorites live in Live's own browser as device presets: every patch parameter is a Live parameter, and loading a preset re-creates the device, so Send on load pushes it.
- Each tone section is one abstraction used 4 times (`Pitch_n`, `TVF_n`, `WG_n`, `VCA_n`, `LFO_n`, `CTRL_n`). **Which sections and page buttons are visible is decided by `js jvpages.js`** in the main patch (tested in `tests/jvpages.test.js`): the Tone tabs (`ToneTabs`), the page buttons (`LFOButton`, `CtrlButton`, `FXButton`, `PatchButton`, `LibraryButton`, `SetupButton`, Hidden parameters, all in the main patch) and the mode switch feed it `tone n`, `page <name> 0/1`, `mode 0/1`; it sends `script show/hide <varname>` to `thispatcher` and `<page> set 0/1` back to the buttons (`route`). One page at a time; switching a page off shows the mode's main view; a tone tab keeps LFO/Ctrl and switches the other pages off. New pages and sections are added in `jvpages.js`, not with message boxes. `JV_LFO` covers tone `0x2D–0x3C` and the LFO depths (`0x4E/4F`, `0x63/64`, `0x75/76`, `0x7B/7C`); its controls have descriptive varnames (`LFO1Rate`, `PitchLFO1Depth`, …). Each LFO block has a shape preview, `jsui jvlfoplot.js` (`prepend wave/rate/offset/delay/fademode/fadetime` from the controls); its math (`curve`) is tested in `tests/jvlfoplot.test.js`. Per-instance Live names live in the main patcher's `parameters.parameter_overrides`. The naming scheme for new parameters is `T<n> <Section> <Param>`.
- Keep the main view uncluttered. Settings you set once (device ID, pacing, and later model and mode) go on the **Setup** page: the embedded bpatcher `Settings`, opened by the outlined **Setup** button at the bottom of the page column. It's styled differently from the tabs on purpose. Don't use overlays: showing a hidden section doesn't reliably bring it to the front in Live, so pages swap content by hiding everything else instead. Settings' outlet sends messages (`deviceid`, `interval`, `sendonload`, `getonpgm`). `route sendonload getonpgm` controls the gate for the on-load push (`live.thisdevice` → `delay 1000` → the push button) and the gate for get-after-program-change; everything else goes to `jv_sysex_queue.js`.
- **Perform mode** (#10, step 1). The `ModeSwitch` `live.tab` (Patch / Perform, stored-only `JV Mode`) at the top of the left column sends `s ---mode` (0 Patch, 1 Perform) and System Common `00` Sound Mode (`expr 1 - $i1` → `js jvparam.js 0 0 0 0`; the JV: 0 PERFORM, 1 PATCH, 2 GM). `jvreceive.js` moves the switch when the JV reports its mode, and after every mode change (not during the first 1.5 s after load) asks for System Common `00–05` (mode, performance number, patch), which the program block follows. Perform mode hides the Tone tabs, LFO/Ctrl/FX/Patch, their sections and `ToneMix`, and shows `PerformPage` (`JV_PERFORM.maxpat`, the **Parts page**: 16 strips with varnames `P<n>On/Channel/Bank/Patch/Level/Pan`, Live names `Part <n> …`; fixed-address senders `js jvparam.js 1 0 <0x0F + n> <off>` behind a `gate` opened only in Perform mode (`r ---mode`), so values restored at load don't write the performance in Patch mode). `bindings.py` traces them as block `part` with the part number in `tones`; the stored bank menu `P<n>Bank` (hidden, fixed list USER, PR-A–E, CARD, EXP-01–19) is op `part_group` (`partGroupToMenu/FromMenu` in `jvsysex.js`, two `expr`s into offsets 2/3). One `js jvparts.js` on the page builds the visible menus `P<n>BankView` (Hidden parameters) from the model and the Setup page's boards (like `jv_wavegroup.js`) and writes each part's patch name into `P<n>Name`: presets and boards from `jv2080_patchnames.js` (**generated** by `tools/import_patch_names.py` from Roland's board documents' patch lists and a local PR-A–E list; never by hand), USER names from the JV (`s ---askname` → `jvreceive.js` queues an RQ1 for `11 nn 00 00`, 12 bytes, only in Perform mode, not in the first 3 s after load and never while a Get/Send runs or the JV loads a performance; the reply goes out as `username n <name>` on outlet 4 → `s ---usernames`). The program block (`jvbank.js`) shows the performance banks (USER, PR-A, PR-B, CARD, p.184) and the stored `Performance Bank` / `Performance Number` (1–32) instead of the program number, and selects a performance with System Common `01` Performance Number (USER 0–31, CARD 32–63, PR-A 64–95, PR-B 96–127), not with a program change, so the control channel doesn't matter; patch bank select and program changes are blocked in Perform mode (`gate`). The name field edits the performance name (one DT1 to `01 00 00 00`, stored in `Perf Name 1–12`). Get reads the temporary performance (`01 00 00 00` common 0x44 + `01 00 1p 00` parts 0x1A, `requestPerformance`); The **Part page**: `JV_PARTEDIT.maxpat`, one instance per part (`PartEdit_1…16`, address `0x10–0x1F` from a message box on `live.thisdevice`, senders `js jvparam.js 1 0 -1 <off>` behind the Perform-mode `gate`; Live names per instance in `parameter_overrides`, `Part <n> …`), traced by `bindings.py` like the tone sections (block `part`, path `PartEdit_{n}`). The part buttons `PartSel1…16` (live.text, two rows of 8, Hidden parameters; `jvpages.js` lights the selected one via `p<n> set 0/1`; a `live.tab` ignores `num_lines_presentation 2` here) sit where `ToneMix` is in Patch mode; `part n` → `jvpages.js` opens `PartEdit_<n>`, and `PartButton` (in LFO's place) toggles between it and the Parts page. The **Keys page** (`JV_KEYS.maxpat`, varname `KeysPage`, button `KeysButton` in Ctrl's place): `jsui jvkeys.js` draws the 16 key ranges and outputs `P<n>KeyLo/Hi <v>` when dragged (`route` → 32 hidden enum numboxes `Part <n> Key Range Lower/Upper`, senders `1 0 <0x0F+n> 17/18`), plus `KeyRangeSwitch` (common `0x2F`); the Parts page's on buttons feed it `part n on v` (`s/r ---partkeys`) to dim parts that are off. Voice reserve: `P<n>Voices` on the Parts page (common `0x2F + n`). `bindings.py` traces `JV_PERFORM` and `JV_KEYS` the same way (`SX_PERF`). Get and panel edits set the part controls (`performance()` in `jvreceive.js`, muted). Send in Perform mode selects the set's performance (`perfselect` → `jvbank.js`), waits 1.5 s while the JV loads it, then writes common/part runs (`perfBlocks`, 150 ms apart). `runs()` bridges gaps of up to 8 unbound bytes with the JV's last-read values (written back unchanged), so each part is one message. The JV answers the first request after loading a performance only after ~0.8 s (measured), so the Perform-mode reply timeout is 2 s; an earlier request gets "Receive data error". The performance address map is in `jv2080_params.js` (`perf`, `part`; `"xp": true` marks `< >` values the JV-2080 ignores). Each part also has its own patch copy at `02 0p 00 00` (part 10: rhythm set at `02 09`), edited on the JV with PERFORM + PATCH.
- Live parameter Long Names must be unique and stable. Renaming one breaks automation and users' saved sets, so do it only on purpose and note it in the changelog.
- Use `---`-prefixed send/receive names so they stay local to the device instance.
- Claude can't run Max, Live or the synth. Every change needs a hardware test by the maintainer, so write test steps in the PR or issue.

## SysEx (Roland DT1)

`F0 41 <dev> 6A 12 <a1 a2 a3 a4> <data…> <sum> F7`

- `dev` is the device ID minus 1. Senders always write `0x10`, and `jv_sysex_queue.js` replaces it with the **Device ID** from the Setup panel (17–32 → `0x10–0x1F`). The checksum doesn't include this byte.
- Checksum: `sum = (128 - (a1+a2+a3+a4+data…) % 128) % 128`. The outer `% 128` is required.
- Temporary Patch (Patch mode): `03 00 00 xx` = patch common; `03 00 10/12/14/16 xx` = tones 1–4.
- System common: `00 00 00 xx`. Performance-mode temporary patches use `02 xx 00 00` and are not supported yet.
- Values with a "#" in the address map, such as the wave number, are split into 4-bit nibbles, high nibble first.
- Wave group (tone `0x01` type, `0x02` id): INT-A/B = type 0, id 1/2; expansion = type 2 (EXP), id = SR-JV80 board number (confirmed on hardware with SR-JV80-11 in slot A). The encoding is the two `expr`s after the hidden `live.menu` in `JV_Wave.maxpat`.
- The visible Wave group control is a `live.menu` set to a **Hidden** parameter (`parameter_invisible 2`: not stored, not automatable) whose list `jv_wavegroup.js` sets with `_parameter_range`, filled `jv_wavegroup.js` from the Setup page's slot menus (`s/r ---boards`). The stored, automatable parameter stays the hidden 21-entry `live.menu`. Never make a *stored* parameter's list depend on settings, because stored values would change meaning. A `live.menu` with `parameter_enable 0` has no item list ("there's no enum"), so use a Hidden parameter for runtime-built menus.
- Values in `< >` in the address map (p.188 note) are JV-1080/XP-80 only and **ignored by the JV-2080**, e.g. System `0x28`/`0x29` Transmit Program Change/Bank Select. Check for `< >` before relying on a parameter. `0x2A` Patch Transmit Channel is `< >` too. Instead, the **JV-2080 reports a patch picked on its panel as a DT1 to System Common `00 00 00 02`**: data = group type (0 USER&PRESET, 2 EXP), group ID (1 USER, 2 CARD, 3 PR-A, 4 PR-B, 5 PR-C, 6 PR-D/GM, 7 PR-E; EXP: board number), patch number as 2 nibbles (0–254). Captured on hardware: USER 1, PR-A 3, PR-E 7, Techno = type 2 / id 11. `jvreceive.js` turns it into `jvpatch type id number` (`s ---jvpatch`), and `jvbank.js` follows silently, then bangs `s ---bangpgm` for the read-back. Never answer it with a program change, which could loop.
- Bank select MSB/LSB for the JV-2080 is on p.184.
- **Models** (#9, Setup → `JV Model`, `s/r ---model`): the JV-1080 (manual pp.132–154) and XP-50 (pp.136–145) have the **same patch tone layout**. Differences: patch common size `4A` / `48` / `49` (JV-2080 / JV-1080 / XP), which `jvreceive.js` uses for Get; and the banks, which `jvbank.js` shows per model (PR-E only on the 2080; GM bank labelled PR-GM vs PR-D; CARD 82/0 not on the XP; PCM card 83/0 only on the 1080, stored as Bank index 23; expansion slots A–H vs A–D). The JV-1080/XP report panel patch changes as program changes (Tx switches `0x28`/`0x29`), not the JV-2080's System Common SysEx. Untested on hardware.

## Testing copies

Only the device in `device/` finds its abstractions and scripts. A copy of the unfrozen `.amxd` elsewhere, such as the Live User Library, fails with "error loading patcher JV_*.maxpat". To use or share it elsewhere, freeze it first. The maintainer has the repo's `device/` folder in Max's File Preferences search path, so copies opened by Live's Edit button and the freeze step can find the files.

## Releases

Check the frozen file's size: v0.2.0 was ~0.6 MB. A jump in size usually means a script used many times `include()`s something.

Freeze the device in Max with the snowflake button, then save it as `dist/JV 2080 Control_<version>.amxd`.
Attach that file to a GitHub Release tagged `v<version>` and upload the same file to maxforlive.com.
Keep version numbers semver and matching on both sites.
